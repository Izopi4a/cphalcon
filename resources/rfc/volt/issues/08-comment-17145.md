A proposal for this one, for v7: #NFR-07 (resolve inheritance on the AST).

With inheritance resolved on the AST before compiling, nested blocks need no new syntax. Blocks are collected by name at any depth, and every block node is replaced by its most derived definition. The parser side is a 12-line change in `base.c`: it stops refusing a block while `block_level > 0`. That check is also what makes a block inside `{% if %}` fail today, since `if`/`for`/`switch` bump the same counter. Patch: https://github.com/Izopi4a/cphalcon/blob/nfr-volt/resources/rfc/volt/prototype/patches/01-nested-blocks.patch

Prototyped on master (5.23.0), with the original case from this issue:

```twig
{# base.volt #}
<html><body>{% block body %}{% endblock %}</body></html>

{# section.volt #}
{% extends "base.volt" %}
{% block body %}
<main>{% block content %}{% endblock %}</main>
<aside>{% block sidebar %}<h3>Help</h3>{% endblock %}</aside>
{% endblock %}

{# leaf.volt #}
{% extends "section.volt" %}
{% block content %}Article{% endblock %}
{% block sidebar %}{{ super() }}<p>Related</p>{% endblock %}
```

```
today:    Phalcon\Mvc\View\Exception: Embedding blocks into other blocks is not supported in section.volt on line 3
proposed: <html><body>
          <main>Article</main>
          <aside><h3>Help</h3><p>Related</p></aside>
          </body></html>
```

- Overriding only the inner block, only the outer one, or neither works, and `super()` works at every level.
- Blocks inside `if`/`for` work as in Twig: the block is always defined, and the condition decides where it renders.
- A block name defined twice in one template becomes an error. Today the last one wins silently.

Examples E1/E2 with captured output: https://github.com/Izopi4a/cphalcon/blob/nfr-volt/resources/rfc/volt/examples.md. The tests are in https://github.com/Izopi4a/cphalcon/blob/nfr-volt/resources/rfc/volt/prototype/tests/Prototype/InheritanceTest.php, next to the same templates failing on the stock build in `tests/Today/InheritanceTodayTest.php`.
